I test the methods that Delimcc-Continuation installs on Pharo's Continuation, and the extension methods of Delimcc-Continuation-Tests on ContinuationTest and TwoInARowStar.

The tests in 'tests - fixes' fail on a stock image, where Continuation>>#value: cuts the whole stack, without running any unwind block, before it restores the captured one: some of them even kill the process that runs them there. The tests in 'tests - api' exercise the methods that ContinuationTest never runs. The tests in 'tests - limits' pin what the package leaves as it is, and the README documents: re-entering a frame runs its captured ensure: blocks again, Exception objects are not part of the snapshot, and whether a temporary is rolled back depends on the temp vectors the compiler chooses. If one of them fails, the semantics changed: update the README. The tests in 'tests - snapshots' check the faster capture and restore: each snapshot holds what the stock capture reads slot by slot, the snapshots stay as captured across re-entries, deep stacks and garbage collections change nothing, and a continuation in the stock layout, captured before the package was loaded, still escapes and re-enters.

Every test asserts something that a value: that does not jump would get wrong, and records in my instance variables, not in temporaries, what has to survive a jump. The exceptions are the tests that run code in other processes, the invocations from another process and the debugger: they fork that code, wait for it with a timeout and keep their state in temporaries. If a fix regresses, a forked process, not the one that runs the tests, runs the captured frames, possibly after the test has ended and nilled my instance variables, so the test fails instead of stopping the run.
